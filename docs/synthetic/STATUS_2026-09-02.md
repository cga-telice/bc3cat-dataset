# BC3CAT-Syn — Status Report

**Date:** 2026-09-02  ·  **Branch:** `synthetic`  ·  **Author:** César

*Supersedes [`STATUS_2026-08-18.md`](STATUS_2026-08-18.md).*

## What this project is doing

We're building a *stressed* version of the BC3CAT construction-catalog dataset for evaluating
retrieval systems. The original dataset is too easy for lexical retrievers because both the
search query and the search result come from the same generation rules (~97 % accuracy with
simple word-matching). BC3CAT-Syn rewrites the catalog text in controlled ways — synonyms,
paraphrases, unit conversions, template restructurings — that preserve the meaning but change
the wording, so retrieval methods actually get tested.

Per-condition detail (achieved n, unique rewrites, reuse, drop reasons, mean token

The machinery: `pantry.py` (approved rewrites + applicability), `variant_budgets.yaml`
(targets/caps/seed as config), `corpus_sampler.py` (deterministic plan with
leaf↔rewrite compatibility) and `corpus_driver.py` (rule emission per slot, composition,
grouped parallel materialization through the frozen s03→s07 rerun, filters, frozen
release + QA report). All fully seeded — the corpus reproduces byte-for-byte.

## César's rulings at the checkpoint (2026-09-02)

1. **Every `all_combined` item rewrites BOTH templates** (one RESUMEN and one TEXTO
   `template_paraphrase`; presence 1 500/1 500). This was the requirement that triggered
   the regeneration; mean token distance in `all_combined` rose 73.7 → 90.0.
2. **`reorder`'s structural absence from `all_combined` is accepted** — full-template
   rewrites collide per field, so with both fields taken by `template_paraphrase` no
   template remains for `reorder`; it is measured in `single_reorder` (1 000/1 000).
3. **Thin-type deficits accepted as-is:** `unit_expansion` 373/650, `unit_conversion`
   209/350 — the approved pantry is small and the ≤20-uses-per-rewrite cap protects
   linguistic diversity over statistical precision (worst-case 95 % margins ≈ ±5.1 /
   ±6.8). Regenerating the thin types stays on the Sprint 40 backlog.
4. **Pantry artifacts kept, documented as stress, no veto:** "tubos tubos" (~376 items),
   "mm mm" (~280), "con topo" → "con topografía" (~245; semantic drift — a *topo* is a
   tunnelling machine). All are traceable per item through the modifications sidecar, so
   downstream analysis can slice them out if needed.

## Problems encountered (and fixed before generation)

1. **Leaf↔rewrite mismatches rendered as silent no-ops.** A rewrite of the value
   *"Diurno"* only surfaces in leaves that actually select *Diurno* — and a plain text
   match also fired on leaves showing *"Diurno Excepcional"*. Fixed with value-precise
   compatibility (exact `(axis, value)` pairs from the original parquet, word-boundary
   fallback). No-op rate fell from ~26 % in the worst types to 0.5 % overall; the
   driver's no-op filter remains as a counted backstop.
2. **One approved rewrite can occupy several slots in a concept** (same fragment under
   different conditions/axes). The driver now emits one rule per slot so the planned
   leaf is always covered; the one same-var duplicate case is resolved by picking the
   leaf's own slot.
3. **Runtime.** Naive per-variant materialization was hours; grouping variants that
   share a `(concept, ruleset)` and materializing each group once in a process pool
   brought the full corpus to ~60 min / 8 workers, with byte-identical output
   regardless of worker count (test-pinned).

## What we're deliberately *not* doing

- No cloud LLM cost — corpus generation is pure CPU; the pantry was built earlier with
  local models via Ollama.
- No merging back to `main` — BC3CAT-Syn is a permanent parallel branch by design.
- No re-litigating the pantry: the review closed under rubric v2 (2 609 A / 202 R) and
  the three artifact families above are kept as documented stress, not silently patched.
- No stacked_2…5 conditions in the pilot — retired by the 2026-08-31 decision; the
  schema still supports them if a future sprint wants them back.
