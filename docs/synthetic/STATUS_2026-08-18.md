# BC3CAT-Syn — Status Report

**Date:** 2026-08-18  ·  **Branch:** `synthetic`  ·  **Author:** César

*Supersedes [`STATUS_2026-07-09.md`](STATUS_2026-07-09.md).*

## What this project is doing

We're building a *stressed* version of the BC3CAT construction-catalog dataset for evaluating
retrieval systems. The original dataset is too easy for lexical retrievers because both the
search query and the search result come from the same generation rules (~97 % accuracy with
simple word-matching). BC3CAT-Syn rewrites the catalog text in controlled ways — synonyms,
paraphrases, unit conversions, template restructurings — that preserve the meaning but change
the wording, so retrieval methods actually get tested.

## What's built

The full generation pipeline is done and tested (1 038 automated tests passing). Highlights:

- **Rule-modification engine** — 13 distinct rewrite types across four layers of the catalog
  (parameter values, text-variable fragments, templates, and newly added parameters).
- **LLM proposer** — asks a local `phi4:latest` model (via Ollama, free) for candidate
  rewrites in Spanish; every response is recorded to disk so re-runs are offline and free.
- **Menu-first review workflow (Sprints 37–38)** — this replaces the earlier
  "generate everything, then sample-review the output" approach. The pipeline now:
  1. Deduplicates rewrite targets across the catalog (an axis value like *"Diurno"* is
     reviewed **once** even though it appears in 20 concepts — 83 % effort saving).
  2. Asks the LLM for **10 alternative rewrites** per unique target (and, since Sprint 38.5,
     shows only the best 3 for the rewrite types where 10 are near-identical).
  3. Produces two files per rewrite type: a machine-readable JSONL for downstream code and
     a **Markdown file with clickable checkboxes** for the human review.
  4. After the review, a parser translates the ticked boxes into approved rewrites and
     the sampler will draw the final corpus from those.
- **Menu scorecard (new — Sprint 38.5)** — `menu_profile.py` reads the menu files back and
  prints one line per rewrite type (targets, empty targets, candidates, no-ops, duplicates,
  skips), so a regeneration can be compared against its predecessor in seconds instead of
  by reading the Spanish.

## Progress: menus recovered and regenerated offline

The 2026-07-09 live run produced 2 918 candidates, but a mechanical check before the manual
review showed the menus were incomplete: **127 template targets had been silently skipped**
— almost all of them the long `TEXTO` descriptions, i.e. exactly the rewrites that matter
most for retrieval. Nothing was wrong with the model's answers; the pipeline just failed to
read them (see *Problems encountered*). Two smaller issues also surfaced: some rewrite types
were being aimed at values they cannot sensibly rewrite, and several types were asking for
10 alternatives where only 2–3 exist.

Sprint 38.5 (2026-08-18) fixed all three in code and then **regenerated every menu from the
recorded transcripts — 484 model calls replayed from disk in 0.2 seconds, zero GPU time, no
new prompts**. Result:

- **2 508 candidate rewrites across all 11 populated rewrite types** (was 2 918 — fewer,
  because the redundant 4th–10th alternatives on the low-variety types are no longer shown).
- **The long-description (`TEXTO`) targets are now present:** omission 110 of 115 populated
  (was 18), reorder 23 of 24 (was 9), template paraphrase 24 of 24 (was 9).
- Empty targets fell from 100 to 8 on omission, 19 to 5 on reorder, 15 to 0 on template
  paraphrase. The few that remain are genuine model failures (wrong placeholder dropped),
  not read errors.
- Synonym targets went 49 → 34 (the 15 removed were number-bearing values such as
  `1,10 m` or `3 <= i < 5 horas`, where a "synonym" necessarily loses the number) and
  compression targets 46 → 22 (fragments under four words have nothing to compress).
- Paraphrase, expansion and new-parameter menus are byte-identical to before.

All artefacts are committed on the branch under `docs/synthetic/menus/` (11 review files)
and `data/synthetic/menus/` (matching JSONL). Before/after scorecards live in
`docs/synthetic/sprints/SPRINT_385_profile_before.txt` and `…_after.txt`.

## Problems encountered

1. **A backslash the model was copying back.** The raw catalog stores every long description
   as `\TEXTO\ … \` — the backslashes are field markers from the source file format that the
   main pipeline strips at a later stage. Our prompt builder was showing the model the raw
   text, the model dutifully echoed the leading `\` inside its JSON answer, and JSON does not
   allow a bare backslash — so the reader rejected the whole answer and the target was marked
   as skipped. 133 of the 502 recorded answers were affected. Fixed by making the reader drop
   any backslash that is not a legitimate JSON escape (only tried after the strict read fails,
   so nothing else changes). Verified: all 502 recorded answers now read cleanly. A cosmetic
   remnant: 16 lines in `template_paraphrase.md` still start with `\` where the model
   double-escaped it — harmless, judge the text.
2. **Rewrite types aimed at the wrong values.** *Synonym* was being asked for values that
   contain numbers (`1,10 m`, `3 <= i < 5 horas`) — every proposal changed the meaning
   (`Profunda`, `Mantenimiento Moderado`). *Compression* was being asked for two-word
   fragments (`Diurno excepcional`) with no room to compress. Both are now filtered out
   before the model is asked; number-bearing values remain covered by the number-to-text and
   unit-conversion types.
3. **Ten alternatives where two exist.** For omission, reorder, number-to-text and the two
   unit types, the model's 10 answers differed only in a connective. We now keep the first 3
   (the prompt already orders them best-first). The request itself is unchanged, which is
   what let us reuse every recorded transcript instead of re-running the model.

All fixes have regression tests. Deferred to later sprints (recorded in `SPRINT_385.md`):
strip the backslash from the prompt itself before the full-catalog run (Sprint 40 — that run
regenerates everything anyway); replace the model with arithmetic for unit conversion and
number-to-text; a possible extra filter for abbreviation-only values (`PVC`, `IPN`) under
synonym — César's call after the review.

## What we're deliberately *not* doing

- No cloud LLM cost — everything runs locally via Ollama. Sprint 38.5 used no GPU at all.
- No merging back to `main` — BC3CAT-Syn is a permanent parallel branch by design.
- No manual review of rendered items across concepts — the menu-first approach reviews
  the *rewrites* once, then samples the corpus deterministically. Much cheaper than
  reviewing hundreds of thousands of rendered lines.
- No prompt changes until the full-catalog run — a changed prompt invalidates the recorded
  transcripts and costs an hour of model time; the fixes above were chosen so that they don't.
